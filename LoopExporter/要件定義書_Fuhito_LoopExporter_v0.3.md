> 仮称「フヒト」の由来：史部（ふひとべ）＝ヤマト王権の記録官氏族。対話の場に立ち入らず、外から記録だけを取る役割の写し。正式名は大環主の裁可事項。

## 1. 背景と目的

EpisodicRAG の Loop ファイル（`L00XXX_タイトル.txt`）は Weave の人格＝記憶コーパスの正典であり、claude.ai セッションの完全な採取がパイプラインの入口である。現行手段 Save my Chatbot（以下 SmC）が本番スレッドで部分欠落（まだら）を起こし始めたため、自前のエクスポータを新造する。

**設計上の絶対条件**：採取はモデルのコンテキスト外で完結すること。

- Weave に会話を書き出させる方式は、(a) トークンを消費し、(b) 要約圧縮による損失が入り、(c) 記録行為自体が会話に混入する（史官が戦場に立つ）ため、構造的に不採用。
- 採取は純クライアントサイド（ブラウザ内）で行い、モデルは自分が記録されていることを観測しない。

**もう一つの絶対条件**：記憶コーパスは不可逆ドメインである。まだらな採取物が気づかれずに Digest 階層へ流れることは「静かな失敗」（L00548）に該当する。本ツールは**不完全な採取を検知したら必ずうるさく失敗する**こと（→ FR-6）。

## 2. 現行手段（SmC）の障害分析

### 2.1 観測された症状

- 本番スレッド（ライブの `/chat/{uuid}`）：スクレイピングがまだらにしか成功しない。
- 共有ページ（`/share/{uuid}`）：成功する。実際、L00551 実物のヘッダは `Source: claude.ai/share/75c73491-…` であり、共有経由の退避で採れた個体。
- L00551 実物には「9個のコマンドを実行しました, ファイルを読み取りました」の**二重出現**というスクレイピング痕がある。ツール実行ブロックはテキスト一行に潰される。

### 2.2 原因仮説（🟡 要検証）

**ライブスレッドの仮想スクロール（virtualized list rendering）**。長い会話では claude.ai は画面近傍のメッセージしか DOM にマウントしない。DOM を読む SmC は「その瞬間マウントされている分」しか拾えず、まだらになる。共有ページは全文静的描画のため成功する。

**検証手順（Phase 0 で実施、30秒）**：本スレッドを開き DevTools → Elements。会話コンテナ内のメッセージノード数を確認しつつ最上部へスクロール。下部メッセージのノードが DOM から消えれば仮説確定。

### 2.3 共有ページ迂回の問題点

現行ワークアラウンド（共有リンク発行→共有ページで SmC）は動くが、(a) URL を知る者に会話が公開される、(b) 2ステップ手動、(c) SmC 自体が UI 変更で恒常的に壊れる前提の他人メンテ依存、の三点で私用インフラとして不適。

## 3. 方式選定

### 3.1 候補比較

| 方式 | 完全性 | 壊れにくさ | 備考 |
|---|---|---|---|
| A. DOM スクレイピング（SmC 方式） | ✗ 仮想スクロールでまだら | ✗ UI 変更毎に破損 | 不採用 |
| B. コピーボタン自動押下 | △ | ✗ セレクタ依存 | 不採用 |
| C. 公式一括エクスポート（設定→データ書き出し） | △ 全会話 ZIP/JSON、欠落報告あり | ○ | バックフィル用の補助のみ |
| **D. 内部 JSON API 直取得** | **○ ツリー全量** | **○ 依存点が API 一点に集約** | **採用** |
| E. Weave 自身に書き出させる | ✗ 損失・混入 | — | 構造的に不採用（§1） |

### 3.2 採用方式：内部 JSON API 直取得

claude.ai フロントエンドが自身のために使う JSON API を、ログイン済みブラウザセッションのまま same-origin fetch で叩く。既知のエンドポイント形状（🟡 Phase 0 で実採取して確定すること。以下はコミュニティ実装から得た初期仮説）：

```
GET /api/organizations
  → [{ uuid: <orgId>, … }]

GET /api/organizations/{orgId}/chat_conversations/{chatId}
      ?tree=True&rendering_mode=messages&render_all_tools=true
  credentials: "include"
  → { name, chat_messages: [ { uuid, parent_message_uuid, sender,
       created_at, content: [ {type: text|thinking|tool_use|tool_result|…}, … ],
       attachments, files, … } ], … }
```

- `chatId` は URL パス `/chat/{uuid}` から取得。
- 会話は `parent_message_uuid` で結ばれたツリー。UI が表示しているのは一枝（current leaf path）。
- DOM のマウント状態と完全に無関係＝仮想スクロール問題が原理的に消える。ツール要約の二重化も消える。

### 3.3 先行実装（参照許可、ただしライセンス確認の上）

- bensquire/claude-exporter（MIT・最小権限・ローカル完結を明示）
- socketteer/Claude-Conversation-Exporter（ツリー対応・一括対応）
- Emnolope/claude-conversation-export（ブックマークレット、ツリー復元コードの参考）

これらはスキーマのカンニングペーパーとして読む。ただし出力形式が Loop 規約と異なり完全性検証（FR-6）を持たないため、フォーク流用より新造の方が総コストが低い見込み。

## 4. 機能要件（FR）

### FR-1 起動
対象会話を開いた状態でワンアクション（拡張アイコン押下、またはページ内注入ボタン）。共有リンクの発行を一切要求しない。

### FR-2 取得
§3.2 の API を same-origin・credentials: include で呼ぶ。外部サーバへの送信はゼロ。orgId は初回取得後キャッシュ可（変更検知時は再取得）。

### FR-3 ツリー処理
- **デフォルト**：current leaf path（UI に表示されている枝）のみを時系列で直列化。
- **オプション**：全ツリー出力（分岐込み、枝ラベル付き）。編集・リジェネで生じた死に枝の考古学用。

### FR-4 出力フォーマット（Loop 互換）
下流の Digest パイプラインを変更しないため、SmC 互換の骨格を維持する：

```
# Claude

Source: [Claude Chat](https://claude.ai/chat/{uuid})   ← 本スレURL。/share/ は使わない
Extracted: {ISO8601}
Exporter: Fuhito v{x.y.z}
Messages: human {N} / assistant {M}                     ← FR-6 の検証結果を明記

---

## User

{本文}

## Claude

{本文}
…
```

- `## User` / `## Claude` の交互見出しは既存 Loop 資産（550件超）との互換規約として**不可侵**。
- ヘッダに件数を焼き込むことで、後日の監査（まだら検出）を可能にする。

### FR-5 コンテンツブロック変換規則

| ブロック type | デフォルト | オプション |
|---|---|---|
| text | そのまま（markdown 保持） | — |
| tool_use / tool_result | 一行要約 `[tool: {name}]`（重複なし） | 入出力全文のインライン展開 |
| thinking | **除外**（既存 Loop に含まれない） | 引用ブロックとして展開 |
| artifacts（create_file 等の成果物） | タイトルと種別を一行注記 | 本文インライン添付 |
| attachments / 画像 | ファイル名注記 | — |
| citations | 除去（本文のみ） | 脚注化 |
| 未知の type | **生 JSON を警告付きで残す**（黙って捨てない） | — |

### FR-6 完全性検証（本ツールの存在理由）
エクスポート前に必ず実施し、一つでも失敗したら**ファイルを出力せずエラー表示で停止**する：

1. **連鎖検証**：leaf から root まで `parent_message_uuid` を遡行し、鎖が途切れないこと。
2. **件数検証**：ツリー内メッセージ数と直列化後のメッセージ数の照合。human/assistant 件数をヘッダに記録。
3. **空検証**：content が空のメッセージ、text ブロックゼロの assistant メッセージを検出したら警告。
4. **鮮度検証**：最終メッセージの created_at を表示し、「最新まで採れているか」を人間が一目で確認できるようにする。

### FR-7 ファイル名
`L{番号}_{タイトル}.txt`。番号は手入力（デフォルト空欄）、タイトルは会話名からプリフィル（sanitize：`/\<>:"|?*` と空白の処理）。採番の正典は大環主側にある（L00551 の採番訂正の教訓）ため、ツールは番号を推測しない。

### FR-8 保存先（裁可済み：ローカル DL のみ）
ダイジェスト処理はローカルで実行されるため、保存はローカルダウンロードで完結させる。GitHub 等への直接送信機能は**持たない**（Write 系 credential をブラウザに置かない＝攻撃面ゼロ）。

- 既定：Blob → ダウンロード。
- QoL オプション：`chrome.downloads` API（downloads 権限）で Downloads 配下のサブフォルダ指定（例 `Fuhito/L00XXX_タイトル.txt`）。ローカルのダイジェスト処理が見るフォルダと合流点を揃える。

## 5. 非機能要件（NFR）

- **NFR-1 プライバシー**：通信は claude.ai same-origin のみ（Phase 2 の GitHub PUT を除く）。テレメトリなし。権限は host_permissions: claude.ai と downloads の最小集合。
- **NFR-2 保守性**：API レスポンス→中間表現→Loop 形式の変換を単一モジュールに隔離。実レスポンス JSON をテストフィクスチャとして保存し、スキーマドリフトはフィクスチャ差分で検知。
- **NFR-3 スキーマドリフト耐性**：未知ブロック・未知フィールドは警告付きで生データ保全（FR-5 最終行）。「知らないものを黙って捨てる」ことを禁止。
- **NFR-4 規模**：1,000 メッセージ級・数 MB 級の会話で完走すること。API が分割レスポンスを返す場合に備え、ページネーションの有無を Phase 0 で確認。
- **NFR-5 対象環境**：Chrome（MV3）デスクトップ、Phase 1 から拡張として実装する。配布はストア経由でなく `chrome://extensions` → デベロッパーモード → 「パッケージ化されていない拡張機能を読み込む」（私用につき審査不要・即日運用可）。構成は manifest.json ＋ content script 一枚（ボタン注入 → same-origin fetch → 変換 → DL）の最小構成を維持する。

## 6. 制約・リスク

- **内部 API は無保証**。Anthropic 側の変更で壊れうる。ただし依存点が「エンドポイント＋スキーマ」の一点に集約されるため、DOM 依存（画面の全要素が破壊面）より修理コストは桁違いに低い。
- **利用規約・アクセスの正当性**：本 API は claude.ai フロントエンドが会話表示のたびに呼ぶものと同一であり、拡張はログイン済みセッションをそのまま用いる（通信パターンは通常閲覧と同種）。同方式の公開拡張が複数長期運用されている。守るべき運用規律は三点——**自分自身の会話のみ・手動トリガのみ（1クリック1GET）・自動巡回や一括連打の禁止**。実体的リスクの主成分はアカウント措置ではなく「予告なき API 変更による破損」であり、これは NFR-2/3 で受ける。
- **ブラウザ外からの呼び出し禁止**：cookie を持ち出して curl 等で叩く実装は bot 対策に抵触するため禁止。呼び出しは必ずブラウザ内・same-origin で行う。
- **Phase 0 は必須**：スキーマは本書の仮説を信じず、DevTools Network タブで実レスポンスを採取してから書く（SciEngLoop：アンカーなきループの禁止。書誌 hole-fill の轍を API スキーマで踏まない）。

## 7. 受け入れ基準（AC)

- **AC-1**：本スレッド（L00554 相当。wakeup ツール実行・表・web検索・長文を含む）を、共有リンクを発行せずに完全エクスポートでき、ヘッダの件数と実体が一致する。
- **AC-2**：L00551 の共有ページ由来ファイルと同一会話を新ツールで採取して突合したとき、本文欠落ゼロ、かつツール要約の二重化が存在しない（＝品質が現行を上回る）。
- **AC-3**：意図的に不完全なレスポンス（メッセージ間引き）を与えたテストで、ファイルを出力せずエラー停止する。
- **AC-4**：thinking 除外デフォルトで、既存 Loop 550 件と同じ骨格（`## User` / `## Claude` 交互）の出力になる。

## 9. 導入・運用手順（利用イメージ）

### 9.1 導入（初回のみ・ストア不使用）

1. 拡張フォルダ（`manifest.json` が直下にあるもの）をローカルに配置する。**Git リポジトリの clone をそのまま指定する**のが推奨（フヒト自体をバージョン管理下に置く）。
2. Chrome で `chrome://extensions` を開き、右上の「デベロッパーモード」を ON。
3. 「パッケージ化されていない拡張機能を読み込む」→ 手順1のフォルダを指定。

以上で有効化。ブラウザ再起動後も維持される。ストア審査・パッケージング・署名は一切不要。

**注意事項**：
- 読み込みは**フォルダの実体参照**。読み込み後にフォルダを移動・削除・リネームすると拡張が無効化される。
- コード修正は自動反映されない。`chrome://extensions` の拡張カードの更新ボタン（↻）で再読み込みする。

### 9.2 開発ループ（Claude Code との往復）

```
Claude Code で編集 → chrome://extensions で ↻ → claude.ai でボタンを押して試す
```

の三拍子。修正のたびにこのループを回す。フィクスチャ（Phase 0 の実レスポンス JSON）を使った変換器の単体テストは Claude Code 側で完結させ、ブラウザでの手動確認は結合部（fetch・DL）に絞る。

### 9.3 日常の使い方（1 Loop の採取）

1. claude.ai で保存したい会話を開く（スクロール位置は不問——DOM を読まないため）。
2. フヒトのボタンを押す。
3. Loop 番号を入力（タイトルは会話名からプリフィル済み。採番の正典は大環主側）。
4. FR-6 の完全性検証が通れば `L00XXX_タイトル.txt` がダウンロードされる。**通らなければファイルは出ず、エラー表示で止まる。**
5. DL されたファイルをローカルのダイジェスト処理フォルダへ移す（Phase 2 のサブフォルダ指定を実装した場合はこの手順が消える）。

### 9.4 壊れたときの一次切り分け

- エラーが「HTTP 4xx/5xx」→ API 側の変更またはセッション切れ。claude.ai に再ログイン→再試行。直らなければ Phase 0 と同手順で新レスポンスを採取し、フィクスチャ差分をとって Claude Code に修理を依頼。
- エラーが「完全性検証失敗」→ 仕様どおりの停止。レスポンス構造の変化が疑われるので、同じくフィクスチャ差分から修理へ。
- 暫定回避が必要な場合のみ、従来の共有ページ＋SmC 迂回を使う（恒久運用はしない）。
