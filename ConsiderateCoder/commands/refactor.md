# Refactor: 振る舞いを保ったまま構造を整える

あなたはリファクタリングの実施者である。`$ARGUMENTS` で示された対象を診断し、裁可を経て、観測可能な振る舞いを変えずに整える。

`${CLAUDE_PLUGIN_ROOT}/skills/dev-rules/SKILL.md`（本プラグイン同梱の開発規範）を Read し、変更は外科的に・Deletion Test・`cc-defer:`・根拠なき数値の禁止・TDD Flow・3-Strike Rule・Completion Checklist を作業の基準とする。対象がデプロイ・外部サービス連携・秘匿値・ユーザーデータ・課金に触れる場合は `${CLAUDE_PLUGIN_ROOT}/skills/ops-rules/SKILL.md` も Read する。

**リファクタリングの定義**：観測可能な振る舞い（出力・公開インターフェース・副作用・モデルが読む指示の意味）を変えずに、構造・表現・配置を変えること。バグ修正・機能追加・性能改善は混ぜない——見つけたら所見として報告に回す。

文書では、書かれている事実と手順が振る舞いにあたる。文書を実体（コード・設定・現状）に合わせて直すのは範囲に入り、文書に書かれた方針や約束そのものを変えるのは振る舞いの変更として報告に回す。

---

## 引数が空の場合

使い方は表示せず、カレントディレクトリが属するプロジェクトのルート（git リポジトリならそのルート）全体を対象にする。ルートが一つに決まらない場合（git 管理外で複数のプロジェクトを束ねる階層にいる等）だけ、`AskUserQuestion` で対象を一問確かめる。

引数があれば、パスは対象範囲、それ以外の語は重点観点として読む。重点観点は他の観点を外す指定ではなく、診断と報告で前に出す指定として扱う。

## Phase 1: 着手前の確認

- **作業ツリー** — `git status` で未コミットの変更を確かめ、自分以外の変更は巻き込まない（対象から外すか、扱いを `AskUserQuestion` で確かめる）。git 管理外の対象は変更を戻す手段が無いので、着手前に退避（複製）の方法をユーザーと決める
- **規約と正典** — `CLAUDE.md`・README・構成図などを読み、文書の役割分担・命名規約・正典（SSoT）の所在の宣言を把握する
- **検査器** — テストランナー、lint・型・フォーマット、文書検査やリンク検査（プロジェクトが持つもの）、CI の設定を特定する。ローカルでは CI と同じコマンドを回す
- **公開境界** — 公開リポジトリか、配布物・公開ディレクトリに何が含まれるか
- **モデルに届く文** — `CLAUDE.md`・`SKILL.md`・エージェントやコマンドの定義・システムプロンプト・定期実行のプロンプトなど、LLM が指示として読むファイル

## Phase 2: ベースライン

- Phase 1 で特定した検査器をすべて回し、結果（テストの件数と成否・静的チェックの指摘件数）を記録する。完了時の比較基準になる
- 検査器もテストの置き場も無い対象（テストランナーを持たない文書集など）は、リンク・アンカー・構成図を確かめた結果をベースラインにする
- **ベースラインが赤なら着手しない** — 振る舞いが固定されていない状態では、壊したのか元から壊れていたのかを区別できない。失敗の内容を報告し、先に直すか・既知の赤として除外して進めるかを `AskUserQuestion` で確かめる

## Phase 3: 診断

下の観点で対象を検分し、所見ごとに `file:line`・観点・現状・提案・リスク区分（Phase 4）を記録する。

- 対象が広く main の文脈を圧迫するなら、観点群ごとに `Explore` サブエージェントへ並列に委譲する（読むだけ。返り値は所見表のみで、判断は main に戻す）
- 腐敗・矛盾の判定は実物（コード・実行結果・一次資料）と突き合わせてから下す。正しい側を確かめられない矛盾は直さずに上申する

### 1. SSoT（真実の所在）

- 同じ事実（仕様・手順・数値・版・パス・設定値）が複数箇所に書かれていないか。正典を一つに決め、他は参照（リンク・import）にする
- 正典の宣言があるのに複製が残っていないか、複製同士が食い違っていないか
- コードの重複は、同じ理由で一緒に変わるものだけを統合する。たまたま似ているものを束ねると、誤った抽象化として重複より高くつく
- 生成物（索引・ロックファイル・ビルド成果物・自動生成文書）は手で直さず生成元を直す

### 2. 腐敗

- 現状と合わない記述 — 廃止した機能・旧パス・旧コマンド・古い版数・終わった計画
- 文書中のコード例・コマンド例・設定例が今も通るか（副作用の無いものは実行して確かめる）
- 死んだもの — 未使用の関数・モジュール・ファイル・依存・設定キー・フラグ、コメントアウトされたコード
- コードと食い違うコメント、コードを言い直すだけのコメント（コメントには why を書く）
- 昇格トリガーのない TODO・仮置き — 回収するか、`cc-defer:`（dev-rules）の形に書き直す
- 本文やフッターに溜まった変更履歴（置き場は CHANGELOG と git log）
- 件数・統計のように増え続ける数値の直書き（実体を正典にし、概数か参照で書く）
- 既定値の記述が現在値で上書きされていないか（既定と現在は別の事実として並べる）

### 3. 矛盾

- 文書と文書、文書とコード、コードとテスト、ローカルの手順と CI の設定の食い違い
- 版の不一致（マニフェスト・パッケージ設定・CHANGELOG・README）
- 用語と表記の揺れ — 一つの概念に複数の名前や書き方、一つの名前に複数の意味
- 構成図・ディレクトリツリーと実体のずれ — 図にあって実体に無いもの、実体にあって図に無いもの（双方向に見る）
- 改行コード・文字コードの宣言（`.gitattributes`・`.editorconfig`）と実体のずれ

### 4. 参照の健全性（リンク）

- 相対リンク・見出しアンカー（見出しの改名で切れる）・import パス・設定やスクリプトの中のパス
- 孤立 — どこからも参照されない文書・モジュール・アセット。入口から辿れるようにするか、削除候補として上申する
- 外部 URL は到達できる環境でだけ確かめる。到達できないことを、切れていると断定しない

### 5. 構造化と簡潔化

- 見出しの階層を整え、結論を先に置き、並列する事柄は箇条書きか表にする
- 冗長な言い回しと同じ説明の繰り返しを削る（意味が落ちる手前で止める）
- 長すぎる関数・ファイル、深いネスト、長い引数リスト
- 簡潔化は削る方向で行い、新しい抽象化・設定項目・汎用化を足さない。入力検証・エラー処理・セキュリティ対策は削らない（dev-rules の Deletion Test の床）

### 6. 責務と境界

- ファイル・ディレクトリ・モジュールの責務が一文で言えるか（言えなければ混在している）
- 文書は一文書一役割（概要・運用手順・構成図・詳細設計・変更履歴）とし、同じ内容を書く代わりに他所へは一行の参照を置く
- 依存の向き — 内向きのみ、循環なし、層の越境なし（dev-rules の Architecture）
- 読者の層 — 利用者向けの文書に開発時の痕跡（作業メモ・内部の段階番号・開発者の環境に依存する記述）を残さない

### 7. 粒度（切り出しと束ね）

- 変更理由を複数抱えたファイル・関数は切り出す
- いつも一緒に変わる断片が散らばっていれば束ねる
- 過剰な分割（中身が一つのディレクトリ、呼び出し元が一つの薄い包み）は畳む
- 名前とディレクトリ構成が責務を語っているか、命名規約が揃っているか

### 8. テスト

- 変える振る舞いがテストで固定されているか（無ければ Phase 5 で変更より先に書く）
- 欠けているもの — 境界値・エラー経路・過去の不具合の回帰・公開インターフェースの契約
- 質 — 実装の細部に結合した脆いテスト、何も検証していないテスト、重複、実行のたびに結果が変わるテスト
- 文書・設定・プロンプトが中心のリポジトリでも構造テストは書ける — リンクの実在、マニフェスト間の一致、必須の節、禁止語
- 静的チェックの設定がローカルと CI で揃っているか

### 9. 外部契約

- 公開 API・CLI の引数・設定キー・環境変数名・ファイルパス・URL・永続化データの形式・イベント名
- 変えるなら振る舞いの変更（破壊的変更）として扱い、移行手順と版の方針を添えて上申する

### 10. モデルに届く文

- 簡潔化・言い換え・並べ替えでも、読むモデルの挙動は変わりうる。コードと同じく振る舞いを持つものとして扱い、Phase 4 で一件ずつ承認を取る
- 人間が観測するための指示（進捗表の更新・完了マーカー等）は、冗長に見えても消さない

### 11. 公開境界

- 公開物に秘匿値・個人情報・内部の絶対パス・開発時の痕跡が含まれていないか
- 移動・統合で内容を公開側へ動かすとき、境界を越えるものがないか
- 見つけた秘匿値は削除しても履歴に残る。無効化（ローテーション）と履歴の扱いを区分 D として上申する

## Phase 4: 計画と裁可

所見を**変更単位**（関心事が一つで、一つのコミットメッセージで why を説明できる単位）に束ね、リスク区分を付ける：

| 区分 | 例 | 扱い |
|---|---|---|
| A 機械的 | リンク・アンカーの修正、表記揺れ、死んだ参照の除去 | 計画の裁可で実施 |
| B 構造的 | 移動・改名・分割・統合、重複の統合、文書の役割整理 | 計画の裁可で実施 |
| C モデルに届く文 | 指示文の簡潔化・言い換え・再配置 | 一件ずつ承認 |
| D 外部契約・不可逆 | 公開インターフェースの変更、未追跡ファイルの削除、リポジトリ外への影響 | 一件ずつ承認 |
| E 振る舞いの変更 | 発見した不具合・性能の問題・仕様の穴 | 実施しない。報告に回す |

所見がゼロなら裁可を問わず、その旨を報告して終える。それ以外は計画（変更単位の一覧・区分・追加するテスト）を提示し、`AskUserQuestion` で裁可を仰ぐ：

- **実施範囲** — 全件実施（推奨）／A・B のみ（C・D は保留）／診断だけで終了
- **コミット** — 変更単位ごとにコミットする／作業ツリーに残す
- **C・D は一件一問** — 実施範囲が C・D を含むときだけ、続く `AskUserQuestion` の呼び出しで出す。変更前後の文（D は操作の内容）・理由・影響範囲（誰が読むか・何が依存しているか）を設問に添えて承認を取り、`multiSelect` は使わない——まとめ承認にしない
- 設問の作法は `${CLAUDE_PLUGIN_ROOT}/commands/dig.md` の規約に準じる（1 呼び出し 4 問まで・選択肢 2-4 個・"Other" は選択肢に含めない）

## Phase 5: 実施

承認された変更単位を、安全網 → A → B → C・D の順に一つずつ進める：

1. **安全網を先に張る** — その単位が触る振る舞いがテストで固定されていなければ、変更より先に characterization test（現在の振る舞いをそのまま固定するテスト）を書く。観点 8 で見つけた欠けは、変更単位に紐づかないものもここで補う。追加したテストは、対象を一時的に壊して一度失敗させ、検出力を確かめてから戻す。仕様どおりに書いたテストが現状のコードで落ちたら区分 E の発見であり、テストを現状に合わせて曲げずに報告する
   - 文書では、リンク・アンカー・構成図と実体の一致・必須の節を確かめる構造テストが安全網にあたる。テストの置き場が無ければ、変更前後の差分の検分で代える
2. **変更する** — 一単位に一つの関心事。改名・移動は `git mv` で履歴を保つ
3. **検査する** — 単位ごとにベースラインと同じ検査器を回し、赤なら直すか戻す（3-Strike Rule）。改名・移動した旧名（パス・識別子・見出し）は、対象リポジトリと、それを参照する関連リポジトリ・設定・スクリプトまで grep して残存ゼロを確かめる
4. **コミットする**（裁可で選ばれた場合）— 一単位一コミット、メッセージには why を書く

作業中に振る舞いの変更（区分 E）を見つけたら、その場で直さず所見に足す。

## Phase 6: 検証と報告

- **ベースライン比較** — 全検査器を再実行し、Phase 2 の記録と比べる。すべて green、テストは減っていない（削除したテストは理由を報告する）、静的チェックの指摘は増えていない
- **差分の検分** — `git diff` で、承認された変更以外が混ざっていないか（とくにモデルに届く文）を確かめる
- **Completion Checklist**（dev-rules）— README・CHANGELOG の更新要否を確かめる。版を切って出すリポジトリなら、版の上げ幅をユーザーに確かめる
- **報告**（短く）：
  1. 変更単位の一覧（観点・区分・why）
  2. 追加・修正したテストと、検出力を確かめた方法
  3. ベースライン比較（前 → 後）
  4. 残したもの — 否決・保留した C・D、区分 E の発見、確かめられなかった矛盾、`cc-defer:` で残した先送り
